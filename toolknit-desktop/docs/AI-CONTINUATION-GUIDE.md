# Karui 工具箱：AI 接手指南

> 最后盘点：2026-09-23。后续模型开始工作前必须先读本文，再读对应架构文档和任务卡。

## 1. 产品所有者的目标

Karui 工具箱已经不只是文件格式转换工具。下一阶段要把它发展成一款更智能、更专业的创作软件，重点包括：

- 多个视频片段合并和非破坏式剪辑；
- 多轨视频、图片、音频、文字和字幕；
- 自动字幕、智能粗剪、参考图修图和 AI 生成；
- 可复用的 AI Skill/工作流；
- 用户偏好、品牌风格、参考素材和创作历史的本地记忆；
- 用户记忆可以查看、修改、遗忘、导出和导入；
- 本地优先，同时允许用户主动配置远程 AI 服务；
- UI 延续 Karui 当前的浅色蓝青品牌、动态背景和中文优先体验。

这里的目标不是一次性完成全部功能。主模型负责定方向、定边界和建立可靠底座，后续 AI 按任务卡逐步实现和优化。

## 2. 当前仓库状态

### 2.1 技术栈

- 桌面框架：Tauri 2.x。
- 前端：原生 HTML、CSS、JavaScript，Vite 5 构建。
- 后端：Rust，通过 Tauri command 提供文件系统、FFmpeg、ComfyUI 和系统能力。
- 媒体处理：打包的 `ffmpeg.exe`。
- AI 文本：DeepSeek、OpenAI、通义千问、Kimi、自定义 OpenAI 兼容端点。
- AI 图片/视频：本地或远程 ComfyUI，通过 HTTP API 提交工作流。
- 文档与表格：pdf-lib、pdf.js、ExcelJS、Chart.js 等。
- 当前没有前端框架、全局状态库、SQLite 数据库和自动化测试框架。

### 2.2 已有能力

- PDF：合并、拆分、旋转、压缩、加密、解密、增强等。
- 图片：格式转换、压缩、图标生成、颜色提取等。
- 音频：转换、裁剪、BPM 检测、从视频提取音频。
- 视频：格式转换；Rust 侧已有媒体探测和 FFmpeg 调用基础。
- AI 文本：润色、翻译、文档生成、表格生成。
- AI Studio：
  - ComfyUI 本地/远程连接；
  - 图片生成；
  - Wan 类视频生成和 API 工作流导入；
  - 模型检测、预设、参数说明、提示词库、草稿和生成结果；
  - VideoHelperSuite 辅助安装。
- 应用基础：中英双语、收藏、最近使用、默认存储路径、系统托盘、安装器。

### 2.3 当前代码事实

- `src/main.js` 已超过 14,000 行，包含绝大多数业务逻辑。
- `src/styles.css` 已超过 15,000 行。
- `index.html` 已超过 5,000 行。
- `src/comfy-studio.js` 已超过 1,500 行。
- 大量偏好、API 配置、收藏、最近使用、提示词库仍保存在 `localStorage`。
- AI API Key 当前也存在 `localStorage`，不适合作为长期安全方案。
- `src-tauri/src/lib.rs` 同时承载多种媒体与系统 command，继续增长会难以维护。
- 没有正式的“创作工程”数据模型，没有多轨时间线，没有撤销/重做命令栈。
- 没有统一任务队列；各工具自行管理进度、取消和子进程。
- 参考图修图尚未完成：现有 ComfyUI 客户端主要提交文本工作流，缺少统一素材上传、遮罩、inpaint/outpaint 工作流和结果版本关系。

## 3. 当前工作区保护规则

后续 AI 必须遵守：

1. 开始前运行 `git status -sb`。工作区可能有用户尚未提交的修改。
2. 不得覆盖或回滚不属于当前任务的文件。
3. 不得使用 `git reset --hard`、`git checkout --` 清理用户修改。
4. 修改大型文件时只做局部补丁；禁止因为格式化工具产生整文件 diff。
5. 不得为了一个新页面重写整个导航、登录、主题或 i18n。
6. 新业务不要继续直接追加到 `main.js`；必须创建独立模块。
7. 新文案必须同时补充 `src/locales/zh.json` 和 `src/locales/en.json`。
8. 新桌面能力必须通过最小权限的 Tauri command 暴露，并校验路径、URL 和参数。
9. 所有外部进程必须支持取消、超时、日志和异常退出清理。
10. 不把 ComfyUI GPL 代码复制进 Karui MIT 主仓库；保持独立进程/API 集成，分发时单独说明第三方许可。

## 4. 每次开发的标准流程

1. 选择 [NEXT-AI-TASKS.md](./NEXT-AI-TASKS.md) 中一个任务。
2. 写出本次“不做什么”，防止任务无限扩张。
3. 先定义数据结构和 command 接口，再写 UI。
4. 实现后至少运行：

```powershell
npm run build
cargo check --manifest-path src-tauri\Cargo.toml
```

5. 涉及 UI 的任务必须用真实页面验证：正常态、空态、错误态、处理中、窄窗口。
6. 涉及媒体处理的任务至少验证：路径含中文、路径含空格、无音频视频、不同帧率、取消任务、输出路径不可写。
7. 更新本知识库中的状态和任务结果。
8. 只有用户明确要求时才提交和推送。

## 5. 架构红线

- UI 不直接拼复杂 FFmpeg shell 字符串；前端提交结构化渲染计划，Rust 负责校验并生成参数。
- 工程文件不保存二进制媒体本体，只保存引用、校验信息和可选代理文件。
- 时间统一使用整数 tick 或“帧数 + 帧率”，不要用浮点秒作为唯一真相。
- 所有编辑都是非破坏式：裁剪只修改入点/出点，不改原文件。
- 预览和最终导出必须使用同一份工程模型，不能出现两套互不兼容的状态。
- 用户记忆默认本地、可解释、可删除；API Key 和密码绝不进入记忆导出包。
- AI 只能提出或生成编辑操作，实际写入工程必须转换为可验证的命令并进入撤销栈。
- Skill 第一版不允许执行任意第三方脚本；先使用声明式清单和受控能力。

## 6. 最容易走错的方向

- 直接在现有“视频转换”页面上堆时间线：它应该是新模块，不是转换页的升级版。
- 一开始就实现 After Effects 级特效：先完成可靠的多轨剪辑和渲染闭环。
- 把“记忆”理解成聊天记录：真正有价值的是偏好、品牌规范、常用导出参数、参考图关系和用户确认过的决策。
- 把所有 AI 都塞进 ComfyUI：字幕、工程规划、媒体分析和渲染调度需要独立服务层。
- 先做漂亮时间线再做工程格式：没有稳定数据模型，UI 很快会推倒重来。
- 直接依赖云端：产品承诺是本地优先，云端能力必须是可选 provider。

## 7. 当前建议结论

下一步不是“再加十个视频按钮”，而是先完成三个底座：

1. 可保存和恢复的 Karui 创作工程格式；
2. 可撤销的编辑命令与多轨时间线状态；
3. 统一后台任务/渲染队列。

底座完成后，片段合并、音频、字幕、参考图修图和智能 Skill 才能共享同一套工程，而不是继续成为彼此孤立的小工具。
